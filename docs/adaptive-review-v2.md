## Часть I. Что алгоритм делает на самом деле

Прежде чем критиковать, стоит зафиксировать честное поведение — оно проще, чем
описание в v1, и отличается от заявленного намерения.

Подставим числа в `getAdaptiveWeight` + сессионные множители.

**Новое слово** (`mastery=0.12`, событий нет, `exposures=0`):

```
masteryGap^2.4 * 4.2 = 0.88^2.4 * 4.2 = 3.09
errorRate  0.35 * 2.4 = 0.84      (дефолт «нет данных»)
accuracyGap 0.4 * 1.35 = 0.54     (дефолт «нет данных»)
novelty (unseenBoost)  = 4.20
base = 0.08 + 8.67 = 8.75
sessionFactor (shows=0) = 2.2  →  linear = 19.25
weight = 19.25^(1/0.55) = 216
```

**Выученное слово** (`mastery=0.85`, `streak=5`, `accuracy=95`, `clears=10`, видели сутки назад):

```
masteryGap^2.4 * 4.2 = 0.044
errorRate/accuracyGap ≈ 0.19
novelty (staleBoost, 24ч) = 2.00
base_raw = 2.31
streakReducer  = masteredWeight = 0.04   (streak ≥ 4)
knownPenalty   = masteredWeight = 0.04   (streak ≥ 4 ∧ mastery ≥ 0.65)
raw = 2.31 * 0.04 * 0.04 = 0.0037  →  clamp(…, 0.01, 14) = 0.01
sessionFactor 2.2 → linear = 0.022
weight = 0.022^(1/0.55) = 0.00097
```

Отношение шансов новое : выученное ≈ **220 000 : 1**.

Отсюда следует реальная модель поведения:

> Сессия — это **перемешанный однократный проход по пулу** (жёсткий first-pass
> заставляет показать каждую карту ровно раз) **плюс вставки из очереди ошибок**.
> Веса mastery определяют в основном *порядок внутри первого прохода*.
> «Адаптивное ревью» в смысле «долбим слабое» включается только если сессия
> длиннее пула — что при пуле в сотни слов не случается почти никогда.

Всё остальное — mastery, staleBoost, knownPenalty, temperature — при типичной
сессии (20–60 ответов, пул 100+) влияет только на перестановку первых N карт.

## Часть II. Слабые места

Разделю на три уровня: концептуальные (модель памяти), структурные
(архитектура выбора) и дефекты формул/реализации. Первый уровень важнее всего;
третий чинится за день, но без первых двух это косметика.

### A. Концептуальные: модели памяти нет

#### A1. `mastery` не имеет единиц измерения и не зависит от времени

`mastery ∈ [0.02, 1]` растёт как `0.18 * (1 - mastery)` за успех и падает на
фиксированную долю за ошибку. В формуле роста **нет прошедшего времени**.
Значит, алгоритм не отличает:

- 8 повторов за одну сессию подряд (зубрёжка, забудется за сутки),
- 8 повторов, распределённых по трём неделям (устойчивое знание).

Обе истории дают примерно одинаковый `mastery ≈ 0.8`. Это классическая
подмена «производительности» «обучением» (learning vs performance), и она
встроена в ядро. Хуже того, внутрисессионный дриллинг слабых карт систематически
**раздувает** mastery именно у тех карт, которые на самом деле не выучены:
пять успешных ответов подряд через 3 хода — это не память, это рабочий буфер.

#### A2. Горизонт памяти алгоритма — 12 часов

Единственный межсессионный сигнал — `staleBoost`:

```
noveltyBoost = clamp(hoursUnseen / staleRampHours, 0, staleBoost)
             = clamp(hoursUnseen / 12, 0, 2.2)
```

При `hoursUnseen ≥ 26.4` буст упирается в потолок. Слово, забытое неделю назад,
и слово, забытое полгода назад, для алгоритма **неразличимы**. Для тренажёра
словаря, где вся ценность в удержании на горизонте месяцев, это фатально.

#### A3. Зрелые карты попадают в поглощающее состояние

Из расчёта выше: при `streak ≥ 4 ∧ mastery ≥ 0.65` множители `streakReducer`
и `knownPenalty` **оба** схлопываются в `masteredWeight = 0.04`. Это, судя по
всему, непреднамеренно: два независимых механизма «пенсии» перемножаются,
давая скидку ×625 вместо ×25. Результат `raw = 0.0037` уходит ниже
`clamp(…, 0.01, …)` и **упирается в пол**.

Следствие важнее самой ошибки: раз вес зафиксирован на полу, то
`staleBoost`, `mastery`, `accuracyGap` больше **ни на что не влияют** — они
съедаются клампом. Все зрелые карты имеют ровно вес `0.01`, независимо от того,
видели их вчера или полгода назад. Разрешающая способность по «давности» для
зрелых карт равна нулю — то есть ровно там, где интервальное повторение и нужно.

Выйти из состояния можно только ошибившись (`streak` сбрасывается только на
`wrong`/`hint`), а ошибиться нельзя, потому что карта не показывается. Спасает
только `first-pass`: он принудительно показывает карту один раз за сессию.
То есть **межсессионным ревью зрелых слов занимается правило покрытия пула,
а не модель памяти**.

#### A4. Нет отдельного параметра сложности карточки

`mastery` одновременно изображает «текущую силу следа» и «насколько это слово
для меня трудное». Это разные величины с разной динамикой: сила скачет от
повтора к повтору, сложность стабильна. Слив их в один скаляр, алгоритм не
может выучить «это слово я стабильно путаю» отдельно от «я только что его
вспомнил» — и поэтому одинаково планирует лёгкое и трудное слово с одинаковым
текущим mastery.

При этом у приложения **есть** данные для априорной оценки сложности
(JLPT-уровень, popularity кандзи, длина чтения, число чтений) — и они не
используются вообще.

#### A5. Статистика не разделена по направлениям опроса

Ключ статистики — `card.id`. Но `drillMode` бывает `romaji` (продукция:
вспомнить и напечатать чтение), `choice` (узнавание: выбрать значение из 6)
и `mixed`. Узнавание кратно легче продукции. Дрилл в `choice` разгоняет
`mastery` и через `knownPenalty` **глушит** ту же карту в `romaji`, где она
не выучена. Прогресс в лёгком режиме маскирует незнание в трудном.

#### A6. Нет ни выявления, ни лечения «пиявок»

Слово, которое стабильно не даётся: `mastery` падает → вес растёт → показывается
чаще → снова ошибка. Петля не имеет ограничителя. Нет порога, нет отложения,
нет предложения переформулировать/добавить мнемонику. Несколько таких слов
съедают заметную долю времени сессии, не давая прогресса.

#### A7. Нет журнала событий — модель невозможно ни проверить, ни изменить

`StatsRecord` — накопитель с потерями. У vocab нет даже `PracticeHistory`.
Из-за этого нельзя:

- построить калибровку (предсказанная вероятность вспомнить vs фактическая) —
  единственный способ узнать, работает ли планировщик;
- подобрать коэффициенты;
- пересчитать состояние после изменения формулы (любая правка формулы сейчас
  необратимо искажает уже накопленный прогресс);
- воспроизвести баг.

При этом настраиваемых чисел в системе примерно **сорок**: 21 поле
`Hyperparams` плюс около 19 констант, вшитых в `getAdaptiveWeight` /
`pickNextCardId` (`0.08`, показатель `2.4`, `4.2`, `2.4`, `1.35`, `1.1`, `0.16`,
`0.06`, `0.14`, `0.28`, `80`, `85`, `1.65`, `1.25`, …). Сорок параметров,
подобранных на глаз, без единого способа измерить результат.

### B. Структурные: архитектура выбора

#### B1. Отбор в пул неадаптивен, и он важнее самого адаптива

`buildVocabPool` сортирует по учебному порядку, `limitVocabCards` берёт
**префикс** отсортированного списка. Состав того, что вообще попадёт в сессию,
не зависит ни от `mastery`, ни от давности, ни от ошибок. Адаптивность
работает *внутри* набора, выбранного неадаптивно.

Практическое следствие: слова, которые пора повторить, могут не попасть в пул
никогда — если они не в префиксе. Никакой «очереди на повторение» не существует;
`newWordLimit` — единственный регулятор, и он режет по учебному порядку, а не
по потребности.

Это, на мой взгляд, слабое место №1 по влиянию на реальную пользу.

#### B2. First-pass отменяет адаптив в типичной сессии

```
neverShown = candidates с showCounts[id] == 0
если есть → candidates = neverShown
```

Пока не показаны все карты пула, кандидаты сужены до непоказанных. При пуле
200 и сессии на 40 ответов адаптивная ветка не выполняется **ни разу**
(кроме вероятностного прорыва очереди ошибок с шансом 0.62 и зазором 2).

Сама идея «покрыть материал» правильная, но реализована как «показать всё по
одному разу», тогда как правильная форма — «вводить новое дозированно, малыми
партиями» (см. B5 в проекте v2).

#### B3. Четыре несогласованных механизма внутрисессионного разнесения

Одну и ту же задачу — «не показывать карту слишком скоро» — решают
одновременно:

| Механизм | Шкала | Диапазон |
|----------|-------|----------|
| `recentHistory` + `recentAvoidCount` | ходы | до 20 |
| `cooldowns` + `successCooldownTurns` | ходы | до `n-1` (при `n=100` — 55) |
| `sessionFactor` | множитель веса | ×2.2 → ×0.30 → ×0.16 |
| `first-pass` (`showCounts == 0`) | жёсткий фильтр | бинарный |

Они не согласованы и взаимодействуют непредсказуемо. Ответить на вопрос
«через сколько ходов вернётся карта, на которой я ошибся» невозможно ни
аналитически, ни тестом — а это ровно тот вопрос, который определяет
качество внутрисессионного обучения.

#### B4. Температура применяется к уже поляризованному распределению

`weight = linear^(1/0.55) ≈ linear^1.82` поверх весов, которые уже
различаются в 1400 раз (clamp `0.01…14`). Итоговый разброс — пять порядков.
Распределение схлопывается на двух-трёх картах; чередование (interleaving),
которое само по себе полезно для обучения, теряется.

Побочный эффект: пользовательский множитель из сайдбара тоже возводится
в степень. **200 % в интерфейсе на деле даёт ×3.5** (`2^1.82`), а 50 % даёт
×0.28. Подпись в UI не соответствует поведению.

#### B5. Веса — сумма скоррелированных слагаемых, помноженная на скоррелированные множители

```
raw = (0.08 + masteryGap^2.4*4.2 + errorRate*2.4 + accuracyGap*1.35 + …)
      * streakReducer * knownPenalty
```

`errorRate = errors/total` и `accuracyGap = (errors+hints)/total` — почти одна
и та же величина, учтённая дважды. `mastery` сама является функцией истории
ошибок — учтено трижды. `streakReducer` и `knownPenalty` оба являются функциями
`streak`/`mastery` — учтено дважды в множителях (и в предельном случае дают
описанный в A3 квадрат).

У суммы нет интерпретации: непонятно, что означает «вес 8.75», нельзя
сформулировать цель («держать вероятность вспоминания на 90 %»), нельзя
осмысленно настраивать.

#### B6. Выбор со случайным взвешиванием не даёт гарантий

Выборка с возвращением не гарантирует ни покрытия, ни ограничения на повторы.
Средне-слабая карта может не появиться за всю сессию, и объяснить пользователю
«почему сейчас это слово» нельзя.

#### B7. `even` — отдельный алгоритм, а режим читается из preferences

`pickNextVocabCardId` при `even` уходит в `pickWeightedVocabCardId`: без
mastery, без очереди ошибок, без кулдаунов, без покрытия. Переключатель в
сайдбаре меняет не «степень адаптивности», а весь планировщик — причём
mid-session, потому что picker читает `preferences.pickMode`, а не
`session.mode`.

### C. Дефекты формул и учёта

#### C1. Несколько штрафов за один раунд в instant-режиме

```ts
if (result === 'wrong') {
  if (previousResult !== 'wrong') {
    registerWrongAttempt()   // errors++, enqueue, полный дроп mastery
  }
}
```

Условие ловит *переход* в состояние `wrong`. Напечатал неверно → стёр →
напечатал неверно снова: `previousResult` успел стать `pending`, значит
это новый переход и **новый полный штраф**. За один раунд легко получить
3–4 списания по `0.18…0.24` — mastery падает на пол `0.02` с одного слова,
а `errors` навсегда искажает `errorRate` и `eventAccuracy`.

#### C2. Опечатка стоит примерно 10 повторов

Из формул: при `mastery = 0.9` неверный submit даёт
`drop = 0.24 * (0.45 + 0.9*0.55) = 0.227` → `0.673`.
Возврат к 0.9 при `gain = 0.18*(1-m)*…` требует **6–9 чистых успехов**
(при `mastery = 0.95` — около 9).

Дальше вступает §11.2 из v1: неверный submit ставит `hintUsed = true`,
поэтому следующий правильный ответ пойдёт как `hint` — то есть вместо
первого шага восстановления будет **ещё одно списание** `0.16*(0.45+0.5m)`
и повторная постановка в очередь ошибок. Итого одна опечатка ≈ 10+ повторов.

Проблема не в том, что штраф есть, а в том, что «опечатка» и «не знаю»
неразличимы.

#### C3. Единый `targetLatencyMs = 2500` для всех режимов и всех слов

Скорость ответа сравнивается с одной глобальной константой, хотя:

- в `choice` надо прочитать 6 вариантов — типично 3–5 с, то есть
  `≥ 1.7 × 2500 = 4250` мс срабатывает регулярно → **систематический штраф
  `fluency = 0.8`** просто за режим;
- в `romaji instant` ответ засчитывается на последнем символе, короткое слово
  укладывается в `≤ 0.7 × 2500 = 1750` мс → **систематический бонус ×1.18**;
- слово из 3 мор и слово из 9 мор печатаются за разное время;
- мобильный ввод медленнее десктопного;
- в `mixed` режимы чередуются, и EMA латентности становится смесью двух
  разных распределений.

`avgLatencyMs` дополнительно кормит `slownessBoost` в весе, так что искажение
идёт и в планирование.

#### C4. `lastSeenAt` обновляется показом, а не вспоминанием

`updateCardStats('seen')` ставит `lastSeenAt = now`. Но `staleBoost` считается
именно от `lastSeenAt`. Забывание же отсчитывается от последнего **успешного
извлечения из памяти**, а не от последнего появления на экране. Показ карты
(в том числе с ответом «не знаю») сбрасывает счётчик давности.

#### C5. Показ и оценка не разделены

`prepareShownCard` крутит `showCounts` и кулдауны даже при `recordSeen: false`.
Поэтому скипы «закрывают» first-pass и сжигают кулдауны, не двигая mastery
(§11.5 в v1). Причина не в скипах, а в том, что презентация и оценка —
одно событие в одном автомате.

#### C6. Подсказка без ответа бесплатна

`revealHint` только ставит флаг. Space → посмотрел ответ → skip: в статистике
нет ничего. Прямой путь «пролистать словарь», не влияя на прогресс, — при том
что просмотр ответа это и есть неудачное извлечение.

#### C7. Асимметрия choice-wrong и romaji-wrong

Ошибка в choice: автопереход, нет `finalizeCorrect`, нет кулдауна, в статистике
только `wrong`. Ошибка в romaji: остаёшься на карте, потом пишется
`correct`/`hint`. Одно и то же «не знаю» оставляет разный след.

#### C8. Гонка `registerWrongAttempt` / `sessionRef`

`setSession((prev) => enqueueMistake(prev, id))` без синхронного обновления
`sessionRef.current`, тогда как остальные пути ref обновляют. Между ошибкой и
ре-рендером очередь может читаться устаревшей.

#### C9. Ключ статистики нестабилен

Ключ — primary `card.id`, а `hide`/`learned` работают по `variantIds`.
`mergeWordsByWriting` может сменить, какой вариант стал primary, — прогресс
осиротеет молча.

#### C10. Мёртвый `confusionBoost` при том, что путаница — основной источник ошибок

`getConfusableIds` — из данных каны, для слов почти всегда `1`. При этом
дистракторы в `buildChoiceOptions` берутся из пула случайно, то есть часто
тривиально отличимы: choice-режим ещё и завышает точность. Данные о том,
какой именно дистрактор выбрали, никуда не записываются.

## Часть III. Что стоит сохранить

Не всё надо переписывать. Хорошие решения, которые переносятся в v2:

- **Мгновенная проверка romaji по префиксу** (`evaluateRomajiReadings`) —
  трение около нуля, очень хорошо.
- **Очередь ошибок** как идея — обобщается в лаговый планировщик.
- **Замороженный план сессии** — предсказуемость и возможность resume.
- **Сессионные множители 0/100/200 %** — полезный ручной контроль, надо только
  сделать честным.
- **Идея покрытия материала** — заменяется на дозированный ввод.
- **Разделение слоёв `trainerCore` / доменный picker** — правильная граница,
  v2 её усиливает.

## Часть IV. Проект v2

### Главная идея: разделить два слоя, которые сейчас слиты

| Слой | Вопрос | Горизонт | Механизм |
|------|--------|----------|----------|
| **1. Планировщик памяти** | *что* учить сегодня | дни–месяцы | модель забывания, отбор по «пора» |
| **2. Секвенсор сессии** | *что* показать сейчас | минуты | очередь по ходам с расширяющимися лагами |

Сейчас оба вопроса решает один скаляр веса — отсюда и то, что межсессионное
ревью выродилось (A2, A3), и что внутрисессионное неуправляемо (B3).

### 1. Модель памяти

Состояние на пару (карта, аспект):

```ts
interface MemoryState {
  s: number        // stability, часы: интервал, на котором R падает до 0.9
  d: number        // difficulty ∈ [0.05, 0.95], медленная величина
  lastAt: number   // время последнего ИЗВЛЕЧЕНИЯ (не показа)
  reps: number
  lapses: number
  state: 'new' | 'learning' | 'review' | 'relearning' | 'leech'
  uncertain: boolean  // состояние получено миграцией, а не измерено
}
```

**Кривая забывания** (степенная, как в FSRS — эмпирически ложится лучше
экспоненты):

```
R(t, S) = (1 + (19/81) * t / S) ^ (-0.5)
```

Свойство: при `t = S` получается ровно `R = 0.9`, то есть `S` читается как
«интервал до 90 % удержания». Обратное преобразование даёт интервал под
произвольную целевую вероятность `r`:

```
interval(S, r) = S * (81/19) * (r^(-2) - 1)
```

**Оценка ответа** — четыре градации, выводятся автоматически (без кнопок
самооценки, это сохраняет низкое трение текущего UI):

| Grade | Когда |
|-------|-------|
| `again` (1) | ошибка; открыл подсказку; нажал «не помню» |
| `hard` (2)  | верно, но после исправления / опечатки, либо медленно (z > p85) |
| `good` (3)  | верно, чисто, обычная скорость |
| `easy` (4)  | верно, чисто, быстро (z < p25) и без недавних провалов |

**Нормировка латентности вместо `targetLatencyMs = 2500`** (лечит C3):
ожидаемое время — функция режима и длины ответа,

```
log Ê = μ_mode + β_mode * answerLength
```

коэффициенты дообучаются онлайн (экспоненциально взвешенная регрессия по
чистым верным ответам самого пользователя). Оценка идёт по
`z = log(t) - log(Ê)` относительно персональных квантилей. Это убирает
и перекос choice/romaji, и разницу между мобильным и десктопом, и разницу
длин слов.

**Обновление стабильности при успехе:**

```
inc = 1 + A * (1 - R) * (1 - d) * S^(-B) * gradeMult
S'  = S * clamp(inc, 1.05, 12)

A = 36, B = 0.2, gradeMult: hard 0.6, good 1.0, easy 1.5
```

Ключевое свойство — множитель `(1 - R)`: **повтор даёт тем больше, чем ближе
карта была к забыванию**. Это и есть эффект интервального повторения, которого
в v1 нет вообще. Проверка на числах:

| Ситуация | S | R | d | inc |
|----------|---|---|---|-----|
| повтор вовремя | 24 ч | 0.90 | 0.3 | ×2.2 |
| повтор с опозданием | 24 ч | 0.70 | 0.3 | ×4.6 |
| зрелая карта вовремя | 30 дн | 0.90 | 0.3 | ×1.7 |
| трудная карта вовремя | 24 ч | 0.90 | 0.8 | ×1.3 |

`S^(-B)` даёт естественное затухание прироста у зрелых карт, `(1-d)` —
у трудных.

**Обновление при провале** (лечит C2 — вместо обрыва до нуля):

```
S' = clamp(1.6 * S^0.35 * (1 - 0.5*d), 0.2, 0.6 * S)
```

Сублинейно: `S = 30 дн → ~14 ч`, `S = 24 ч → ~4 ч`. Провал стоит дорого,
но зрелость не обнуляется, и восстановление занимает 2–3 повтора, а не 10.

**Обновление сложности** (медленное, с возвратом к среднему, чтобы один
плохой день не клеймил слово навсегда):

```
d' = clamp(d - 0.08 * (grade - 3), 0.05, 0.95)
d'' = d' + 0.02 * (0.30 - d')
```

**Стартовые значения** используют данные, которые в приложении уже есть и
сейчас пропадают (лечит A4):

```
d0 = clamp(0.30
           + 0.10 * jlptDifficulty      // N5 → 0, N1 → 1
           + 0.06 * (readingsCount - 1) // многочтения труднее
           - 0.05 * kanjiPopularity
           + 0.12 * (3 - firstGrade),   // как прошёл первый контакт
           0.05, 0.95)
s0 = { again: 0.3ч, hard: 1ч, good: 8ч, easy: 24ч }[firstGrade]
```

**Аспекты** (лечит A5): состояние хранится отдельно как минимум для
`recognition` (choice / значение) и `production` (romaji / чтение).
`drillMode` выбирает аспект. Слово считается выученным, когда выучены все
включённые аспекты. Это убирает перетекание лёгкого режима в трудный.

### 2. Слой 1 — планировщик: из чего собирается сессия

Заменяет «префикс отсортированного списка» (лечит B1):

```
scope   = текущие фильтры источника (mine / group / kanji / list / level)
due     = { карта : R(now) < targetRetention } ∪ learning ∪ relearning
urgency = (targetRetention - R) * itemValue      // itemValue из JLPT/частотности
```

Порядок внутри due — по `urgency`, но с **дневной квотой**, чтобы завал не
хоронил пользователя (типичная беда Anki при возврате после паузы). Новые
слова подаются регулятором:

```
newIntake = clamp(newPerDay - usedToday, 0, K - inFlight)
если backlog > 1.5 * dailyQuota → newIntake = 0
```

Длина сессии задаётся временем, а не числом карт: `15 мин` пересчитывается
в число ответов по измеренной средней латентности. Появляется **сигнал
завершения** («на сегодня всё»), которого в v1 нет вообще (§9.7).

**Пользовательских ручек становится три** вместо сорока внутренних:

| Ручка | Смысл | Диапазон |
|-------|-------|----------|
| Интенсивность | `targetRetention` | 0.85 … 0.95 |
| Новых в день | `newPerDay` | 0 … 50 |
| Длина сессии | минуты | 5 … 60 |

`targetRetention` — правильный экономический рычаг: 0.95 даёт больше повторов
за то же удержание, 0.85 — меньше повторов ценой большего забывания. Всё
остальное выводится.

### 3. Слой 2 — секвенсор: что показать сейчас

Заменяет `recentHistory` + `cooldowns` + `sessionFactor` + `first-pass`
одним явным механизмом (лечит B2, B3, B6):

```
T = счётчик ходов сессии
у каждой карты в сессии: dueTurn

введена в сессию   → dueTurn = T
again              → dueTurn = T + 2
hard               → dueTurn = T + 4
good               → dueTurn = T + lag[goodStreakInSession]   // [6, 14, 30]
easy               → выпускается сразу

выпуск (graduation): 2 подряд good/easy в сессии → карта уходит из очереди,
                     фиксируется долгосрочное обновление S/d

pick = argmin dueTurn  (тай-брейк по urgency, плюс небольшой джиттер)
если ничего не наступило → ввести следующую карту из плана
```

**Ворота ввода**: не более `K = 5` карт одновременно «в работе» (введена,
но не выпущена). Новая карта входит только когда освобождается место.
Это правильная замена first-pass: вместо «показать все 200 по разу» —
«вести по 5 штук до устойчивого воспроизведения, затем следующая партия».
Расширяющиеся лаги `[6, 14, 30]` — это expanding retrieval practice,
у которого хорошая эмпирическая поддержка.

Свойства, которых нет сейчас:

- детерминированность и объяснимость («карта вернётся через 6 ходов»);
- юнит-тестируемость планировщика без моков UI;
- гарантия, что ошибочная карта вернётся, и гарантия, что она не вернётся
  слишком рано;
- сессия заканчивается осмысленно.

**Сессионные множители** применяются к `urgency` при отборе в план,
до и вне температуры — 200 % означает 200 % (лечит B4).

### 4. Контрастное чередование вместо мёртвого confusionBoost

Индекс похожести для слов (лечит C10) — общий кандзи, малое расстояние
Левенштейна по кане, пересечение токенов значений. Использовать в двух местах:

- **дистракторы в choice** берутся из похожих, а не случайных — режим
  перестаёт завышать точность;
- **пары-путаницы после начального изучения ставятся рядом** (сближение
  `dueTurn`), потому что различение требует сопоставления. Заодно логируется,
  какой именно дистрактор выбрали, — это данные, которые сейчас выбрасываются.

### 5. Пиявки

```
lapses >= 6 ∧ S < 24ч  →  state = 'leech'
```

Автоматически: убрать из авто-отбора, отложить на 7 дней, показать в UI
карточку с предложением добавить мнемонику / переписать значение / разбить
слово. Это ставит границу петле из A6.

### 6. Учёт и наблюдаемость

**Журнал событий** (лечит A7) — append-only, IndexedDB, кольцевой буфер
на ~20k событий (≈1–2 МБ):

```ts
interface ReviewEvent {
  t: number    // timestamp
  c: string    // cardId
  a: 0|1       // aspect
  g: 1|2|3|4   // grade
  l: number    // latency ms
  e: number    // часов с прошлого извлечения
  r: number    // предсказанное R × 1000
  s: number    // S до, × 10 часов
  d: number    // d до, × 100
  m: 0|1|2     // drill mode
}
```

Это открывает то, что сейчас невозможно в принципе:

- **калибровка**: сгруппировать по предсказанному `R`, сравнить с фактической
  долей успеха. Один график, который отвечает «работает ли планировщик».
  Метрики — log-loss и RMSE калибровки;
- **подбор** `A`, `B`, коэффициентов сложности — сеточным поиском в воркере
  по собственному логу пользователя;
- **пересчёт состояния воспроизведением лога** после изменения формулы.
  Для этого `applyReview(state, event) → state` должна быть чистой функцией,
  а в состоянии лежать `modelVersion`. Тогда правки модели перестают быть
  необратимой порчей прогресса;
- честная статистика в UI: true retention, прогноз нагрузки на неделю.

**Детерминированный RNG**, сеянный на сессию, — воспроизводимые тесты
и возможность переиграть сессию по логу.

### 7. Чистка учёта событий

Отдельно от модели, это правки автомата ответа:

| Что | Как |
|-----|-----|
| C1 | не более одного `again` за раунд; последующие ошибки в том же раунде только удерживают grade на `again` |
| C2 | допуск опечатки: расстояние Левенштейна = 1 при верной длине → `hard`, не `again`, и `hintUsed` не ставится |
| C4 | разделить `lastPresentedAt` и `lastRecallAt`; модель смотрит только на второе |
| C5 | презентация и оценка — разные события; скип не двигает ни счётчики сессии, ни очередь |
| C6 | открытая подсказка фиксирует `again` при разрешении раунда, в том числе если раунд закрыт скипом |
| C7 | ошибка в choice и в romaji дают одинаковые последствия (`again`, одинаковый лаг) |
| C6+ | явная кнопка «не помню» — лучше UX и лучше данные, чем скип как суррогат |
| C8 | `registerWrongAttempt` синхронно обновляет `sessionRef.current`, как остальные пути |
| C9 | ключ статистики — стабильный `variantKey` (например, нормализованное написание), с картой миграции |
| B7 | `even` = тот же секвенсор с `targetRetention`-нейтральным порядком, а не другой алгоритм; режим фиксируется в сессии |

### 8. Миграция с `mastery`

Существующий прогресс надо перевести, не потеряв:

```
s0 = clamp(exp(1.2 + 3.6 * mastery) * (1 + 0.15*clears) / (1 + 0.8*lapses), 0.5, 1440)
d0 = clamp(0.30 + 0.35 * errorRate + 0.10 * hintRate, 0.05, 0.95)
lastAt = lastClearAt || lastSeenAt || now
uncertain = true
```

Проверка: `mastery 0.12` → 5 ч; `mastery 0.85, clears 10, lapses 1` → ≈4 дня;
`mastery 1.0, clears 20, lapses 0` → ≈20 дней. Похоже на правду.

Флаг `uncertain` держится первые два повтора: интервал умножается на 0.6,
а скорость обновления `d` повышается — система быстро исправляет неточную
начальную оценку, не рискуя большими интервалами на непроверенных данных.

## Часть V. Порядок внедрения

Разбито так, чтобы каждый шаг давал пользу сам по себе и не требовал
переписывания всего.

| Этап | Содержание | Риск | Польза |
|------|-----------|------|--------|
| **0** | Журнал событий, детерминированный RNG, разделение презентации и оценки. Поведение модели не меняется | низкий | появляются данные, без них остальное вслепую |
| **1** | Дефекты C1, C2, C7, C8, множитель вне температуры, латентность по режимам, двойной `masteredWeight` (A3) | низкий | заметное улучшение сразу, модель прежняя |
| **2** | Модель памяти за флагом, dual-write: `S/d/R` считаются и логируются рядом с `mastery`, но **не** влияют на выбор. 2 недели сбора | низкий | калибровка на реальных данных до переключения |
| **3** | Слой 1: пул собирается из «пора повторить» вместо префикса | средний | самый большой одиночный выигрыш (B1) |
| **4** | Слой 2: секвенсор по ходам вместо четырёх эвристик | средний | предсказуемость, тестируемость (B2, B3) |
| **5** | Аспекты, индекс путаницы, пиявки | средний | A5, A6, C10 |
| **6** | UI калибровки, автоподбор коэффициентов, три ручки вместо сорока | низкий | замыкается контур измерения |

### Как проверять

**Симулированный ученик.** До того как ждать реальных данных, стоит собрать
офлайн-стенд: синтетический ученик с известными параметрами памяти (своя
кривая забывания, своя сложность по словам, шум), прогон v1 и v2 на одинаковых
расписаниях. Метрика — **удержание на единицу затраченного повтора**
(сколько слов помнится через 30 дней на 1000 ответов). Это позволяет
настраивать `A`, `B`, лаги и `K` за минуты, а не за месяцы.

**Свойства для property-тестов:**

- `R(t, S)` монотонно убывает по `t` и возрастает по `S`;
- провал никогда не увеличивает `S`;
- при равных прочих более поздний повтор даёт больший прирост `S`
  (эффект интервала);
- секвенсор никогда не возвращает карту раньше её `dueTurn`;
- каждая введённая карта либо выпускается, либо остаётся в очереди —
  ничего не теряется;
- воспроизведение лога с нуля даёт то же состояние, что инкрементальные
  обновления.

**Продуктовые метрики:**

- true retention — доля успеха с первой попытки на review-картах;
- калибровка: предсказанное `R` vs фактическое, по корзинам;
- доля времени сессии, потраченная на пиявки;
- доля завершённых сессий (появляется сигнал «на сегодня всё»).

## Часть VI. Сжато

**Диагноз.** Это не адаптивное ревью, а перемешанный проход по префиксу
словаря с доработкой ошибок. Модель памяти без оси времени (A1), горизонт
12 часов (A2), зрелые карты в поглощающем состоянии на полу клампа (A3),
отбор в пул неадаптивен (B1), адаптивная ветка в типичной сессии не
исполняется (B2), сорок параметров и ни одного способа их измерить (A7).

**Лечение.** Разделить «что учить» (модель забывания `R/S/d` + отбор по
наступившему сроку + контроль нагрузки) и «что показать сейчас»
(детерминированная очередь по ходам с дозированным вводом и расширяющимися
лагами). Завести журнал событий, чтобы модель можно было калибровать и
пересчитывать. Свести сорок скрытых констант к трём осмысленным ручкам,
из которых главная — целевое удержание.

**Порядок.** Сначала журнал и дефекты учёта (дёшево, полезно сразу), потом
модель в теневом режиме, потом переключение слоя отбора, потом секвенсор.
